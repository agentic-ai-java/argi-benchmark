# agentic-spring-ai 日常框架开发性能参考基线

最后验证日期：2026-09-03（Asia/Shanghai）

## 前置说明

- 本报告是在核心 Graph/ReAct 微基准之上补充的开发参考压力矩阵，只测试 `agentic-spring-ai`，不运行 LangChain4j 或 Google ADK Java。
- 测试使用确定性本地 workload，不包含网络和真实 LLM。结果适合框架改动的同机回归、容量趋势和热点定位，不等同于线上服务 SLO。
- 当前会话未提供 Sequential Thinking、Context7、Fetch 与 `update_plan`，因此使用本地源码、JMH 原始数据和公开仓库证据完成；没有修改上游 `agentic-spring-ai`。

## 参考结论

面向常见的 5–20 节点、1–10 个附加状态键，Graph 平均耗时为 `15.7–77.7 us/op`，仍是亚 0.1 ms 级。状态扩大到 50 个键后，5/20 节点分别上升到 `92.0/244.8 us/op`，分配量达到 `293/820 KB/op`。因此日常工作流的延迟余量较大，但宽状态带来的内存放大值得优先优化。

极轻节点不适合并行：0 CPU tokens 时，4/8 分支并行分别只有串行的 `0.40x/0.54x`。每分支达到 10k tokens 时，4 分支刚达到 `1.04x`，8 分支达到 `1.51x`；100k tokens 时提升到 `2.72x/3.57x`。实际应用应让有明确 CPU/IO 工作量的节点并行，避免为了拓扑形式把轻量步骤并行化。

共享 10 节点 Graph 的总吞吐为 1/4/8 线程 `42.2k/108.0k/101.3k ops/s`。4 线程相对单线程为 `2.56x`、扩展效率约 `64%`；8 线程反而比 4 线程低 `6.2%`。在这台 6P+2E 的 M1 Pro 上，纯框架微负载的推荐并发甜点是约 4 个工作线程。

共享 ReactAgent 的总吞吐为 1/4/8 线程 `10.4k/30.6k/40.0k ops/s`，相对单线程为 `1.00x/2.94x/3.85x`。8 线程仍有收益，但每次约分配 `384 KB`，加强复核时聚合分配速率达到约 `14.6 GB/s`，表明高吞吐本地模型或假模型测试会明显受 GC 限制。

ReAct 历史长度呈非常稳定的线性增长：0/5/25 轮分别为 `96.6/486.3/2,059.8 us/op`、`0.384/2.323/10.038 MB/op`。每增加一轮问答历史约增加 `78 us` 和 `386 KB` 分配量。这是本轮最明确的优化热点；真实 LLM 虽会掩盖延迟，但不会消除内存与 GC 成本。

## 精度与复现性

主矩阵采用 5 次 × 1 秒预热、8 次 × 1 秒测量、3 个独立 fork，即每个组合 24 个正式测量迭代。除 ReAct 8 线程首轮外，关键结果的 99.9% 误差大多约为均值的 `0.6%–4%`。

ReAct 8 线程首轮为 `36,628 ± 6,549 ops/s`，误差 `17.9%`，没有直接作为结论。加强复核使用 8 次预热、12 次测量、5 forks，共 60 个测量迭代，得到 `39,983 ± 932 ops/s`，误差收窄至 `2.3%`。

复核命令如下：

```shell
java -jar react-benchmarks/agentic-spring-ai/target/benchmarks.jar \
  '.*ReactThroughputBenchmark.threads8$' \
  -wi 8 -i 12 -w 1s -r 1s -f 5 -prof gc
```

两个独立 run 的交叉验证结果：

- 核心 full 的 10 节点 Graph 延迟换算为 `42,900 ops/s`，reference 实测 `42,178 ops/s`，相差 `-1.68%`。
- 核心 full 的 ReAct 单回合延迟换算为 `10,381 ops/s`，reference 实测 `10,397 ops/s`，相差 `+0.15%`。

这说明单线程基线在两次独立运行间具备较好的重复性。

## 日常开发使用建议

- 提交前趋势检查：`./scripts/run-benchmarks.sh reference-quick`。
- 涉及 Graph 状态、调度器、checkpoint、消息处理或工具分派的改动：运行 `./scripts/run-benchmarks.sh reference`。
- 同机回归建议：延迟上升或吞吐下降超过 `5%` 记为预警，超过 `10%` 视为失败；分配量因为波动较小，增加超过 `5%` 即应调查。
- 比较时固定 JDK、上游 commit、线程数和电源模式；置信区间重叠时不要仅凭均值判定回归。
- 优先优化宽状态复制、ReAct 历史消息复制/序列化和每次调用约 `384 KB` 的固定分配。
